# 开发指南

## 设计原则

**一等实体是"问题 → 解决方案"，不是工单。**

- 工单只是对话容器，不是一等实体。说不清一个概念沉淀什么资产，就砍掉它。
- 平台风格对齐：决议之于 delib = 解决方案之于 support；蒸馏隐式经验的范式来自 agent 云，这里是把它用在客户边界上。
- AI Native 不是加聊天机器人，而是"AI 应答 → 升级人工 → 蒸馏回资产"这个循环本身。建的是循环，不是客服入口。

## 客户端分端

按访问者类型分两端：

| 端 | 访问者 | 状态 |
|---|---|---|
| studio | B 端 | 已有骨架（`src/studio`，Flutter Web，侧边导航：问答 / 工单 / 知识库） |
| lite | 内外部 C 端 | 未建 |

- 代填是权限问题，不是端的属性：有权限者（如内部人员）可替外部客户填，自己填也行；填在哪端取决于他有哪个端的权限。
- 工作日志、送确认、提炼方案等工作面归属哪端，待部署定位确定后落。

## 资产模型

四类资产，按优先级：

1. **解决方案库**（核心）——问题→答案配对 + 诊断路径。支持域的同构痛点是"解决方案不可见"：每个支持人员重复解同一个问题。资产视图（复用率、高频问题榜）是第一个治理视图。
2. **蒸馏规则**——诊断树、路由规则、升级判据、支持智能体。AI 第一线应答的本体。
3. **需求与缺陷信号**——结构化抽取，喂给需求地图。
4. **原始交互档案**——永不丢弃，是 2、3 的语料和审计依据。

**边界**：

- 客户知识（客户档案本身）归 quanttide-customer 域，本云是写入者之一，不另起炉灶。
- 给客户的知识（FAQ/教程/案例）落领域仓库 docs/（tutorial、gallery、handbook），本云是产生者。

## 数据形状

**先最小闭环，后实体表。** 不预先设计实体关系图，数据形状从真实使用中长出来。

验证标准是最小闭环全链路跑通：

> 一个真实客户问题 → AI 用现有资产试答 → 答不了，人补充 → 蒸馏成解决方案条目 → 下一个同类问题被 AI 直接答掉

闭环跑通之前，不堆功能。

## 仓库结构

```
src/studio/       # B 端工作台（Flutter Web）
src/lite/         # C 端轻客户端（未建，占位）
docs/user-guide/  # 用户指南——预期使用方式
docs/dev-guide/   # 本文档——开发原则与路线
```

领域骨架（data×11、docs×6 等资产位）在 `domains/quanttide-support`，本仓库是其中的可部署应用。

## 当前状态与下一步

studio 已有骨架（问答 / 工单 / 知识库四屏，种子数据为 journal 案例快照）；lite 未建。下一步仍是实现最小闭环（资产库先以最简形态存在——哪怕只是一组结构化文档，能被 AI 检索和写入即可），在真实客户问题上验证循环。
